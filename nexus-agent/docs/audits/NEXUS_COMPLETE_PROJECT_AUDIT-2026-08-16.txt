35. P3 ANALYSIS (from actual implementation)
================================================================================
- How chunks are formed: _chunk_intent_units sequential dependency-
  ordered groups of chunk_size=6 with boundary shift (semantic_parser_node
  .py:709-762); interleaved partition optional (P3 knob, default off);
  rotation/concurrency knobs exist (defaults = control).
- Partitioning deterministic? YES — pure functions of (units, relationships
  , settings); same input -> same chunks every run.
- Chunk sizes predictable? YES (ceil(n/6) with boundary shifts; W135
  -> [6,6,6,2]).
- Latency correlates with unit count? NO — evidence: chunk [6,6,6,2]
  slowest was chunk 1 (6 units) in 7/7 rotation runs AND the 2-unit chunk
  4 was sometimes slowest; per-call variance 6-192s for identical content
  (15 runs, 0 failures/fallbacks). Content composition matters more than
  count, and endpoint variance dominates both.
- Can chunks be safely rebalanced? Yes mechanically (merge + coverage
  invariant are partition-agnostic; verified in code), but measurement
  shows no max(chunk_latency) benefit (interleaved median ~86s vs control
  ~87.7s; chunk_size=4 worse).
- Would adaptive balancing violate intent coverage? NO by construction —
  coverage recovery at merge is partition-agnostic (semantic_parser_node
  .py:960-1011); refs/deps reassigned at merge.
- Would it increase endpoint contention? Yes — more chunks = more
  concurrent calls to the same NIM endpoint (measured: 5 concurrent
  chunks no better).
- Do smaller chunks increase total LLM overhead? Yes (more calls, more
  prompt tokens, more merge work; measured chunk_size=4 worse).
- Is P3 worth implementing? NO as designed — FALSIFIED by 15 runs
  (closed negative, commit 1cce159). The real lever is endpoint-side
  (per-call variance / connection pooling), which is provider-scope.
P3 BENEFIT: none measured; theoretical only if endpoint variance shrinks.
P3 RISK: churn on frozen-adjacent planning code; coverage risk none.
P3 COMPLEXITY: low (knobs exist).
P3 EXPECTED IMPACT: nil on max(chunk_latency) (measured).
P3 RECOMMENDATION: do not implement; keep knobs as diagnostics; if the
NIM endpoint stabilizes, re-run the A/B before touching anything.
